# Server boundary, relational data and latency metrics

**Purpose:** Bridge browser-side intuition to server request hops, database-enforced invariants/indexes, and tail-latency saturation vocabulary before diving into concurrency, locks, and scaling.

**Lane:** foundation. This is a fast diagnostic bridge for frontend-to-backend engineers, not a textbook chapter or timed day.

## Capability map
- `server-request-lifecycle-and-network-boundaries:explain`
- `relational-constraints-and-index-cost:explain`
- `latency-percentiles-and-capacity-metrics:explain`

The map is available scope, not proof of active enrollment. Inspect goal membership and unfinished work first. Clear any foundation concept the learner already commands quickly; teach missing ones from first principles before moving into B1/B2/B6.

## Interactive case
A browser sends `POST /orders` through a reverse proxy to a Node.js API backed by PostgreSQL. Average response time is 40 ms, p95 climbs to 1,800 ms during checkout bursts, and one caller times out at the proxy after 5 seconds while Postgres still commits the row. Ask the learner to separate what the client observed from what happened at each boundary, and what happens when a lookup query lacks an index on a 2M-row table.

The teacher answers the learner's questions about the case, asks for one discriminating explanation or prediction, and waits.

## Freeze only the selected claim
- **Network boundary:** distinguish client timeout/proxy disconnect from server/DB completion; separate transport errors from application status codes.
- **Relational constraints & indexes:** explain why `UNIQUE`/`CHECK` constraints enforce invariants across all callers while missing indexes turn point lookups into sequential scans that inflate query duration and CPU.
- **Latency & capacity metrics:** distinguish p50 vs p95/p99, service time vs queueing time, and utilization vs saturation (including why averages hide tail spikes).

## Smallest useful repair
Anchor every repair in a frontend contrast: `fetch()` rejection is not proof of server rollback; client-side form validation is not a `UNIQUE`/`CHECK` database invariant; Lighthouse average load time hides what p95/p99 reveals under multi-user concurrency.

## Branch and return
Optional: TCP handshake/keep-alive tuning or B-tree page layout internals only after the practical request-path and query-cost boundaries are clear.

## Closure and notes
Close each foundation objective once the causal distinction holds cleanly; do not pad with trivia once the learner can use the vocabulary in B1/B2/B6.

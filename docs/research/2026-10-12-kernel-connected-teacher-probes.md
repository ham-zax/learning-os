# Kernel-connected fresh-teacher probes — 2026-10-12

**Scope:** One bounded, synthetic dogfood batch over four of the existing sixteen tracked teacher scenarios. These are genuine isolated model runs and public-kernel calls, **not** human learner sessions, cross-provider evaluations or long-term learning outcomes.

## Execution boundary

- Host: non-ARM WebHarness/WSL; repository baseline `6fb0942`.
- Each case was generated with `npm run -s eval:teacher -- prepare CASE_ID /tmp/.../CASE_ID`, creating an isolated synthetic SQLite database **outside the repository**. The model was instructed not to access `data/profiles/**`, evaluator source, gold checks or unrelated state.
- OpenAI Codex CLI model as reported by invocation logs: `gpt-6.1-sol`, low reasoning effort, ephemeral individual sessions, `workspace-write` sandbox rooted at `/tmp/learning-os-tracked-probe-20261012`. The model could read the repository's Teacher skill and protocol and invoke the **public kernel** against the synthetic database.
- Initial `npm run -s kernel -- --db ...` attempts failed because the sandbox disallowed `tsx`'s local IPC listener (`listen EPERM ... /tmp/tsx-1000/33.pipe`). **One original causal-model session recovered via `node --import tsx src/kernel-cli.ts` and did write to the synthetic database.** Its subsequent reuse by the originally reported final causal session contaminated the 3/3 attribution, as independent review B2-F1 confirmed. Those two causal sessions are **excluded from the final attributable set**; their logs remain diagnostic evidence. The other cases used the built `node /home/hamza/repo/learning-os/dist/kernel-cli.js --db ... METHOD [args]`, the same public kernel without the IPC listener.
- Every **credited final case** used its own fresh synthetic state, resumed the frozen attempt via `getStudyContinuation`, made public kernel calls, and saved the actual learner-facing reply. Following B2-F1, the causal case was run again with a **newly prepared, previously untouched database** (`/tmp/learning-os-b2f1-fresh-d1Z7MF/case/tutor.db`) using the atomic `recordExposure` `reconstructionQuestion` input. The new single public state-changing call persisted both the question and exposure before emitting the exact recorded reply. Inspections used `node dist/evaluation/cli.js inspect` with the actual reply (or equivalent `npm run -s eval:teacher -- inspect`). Logs and replies remain outside version control, with corrected SHA-256 fingerprints below.

## Disposition and limits

- Narrow teacher-protocol change: explicitly tell a resumed scaffold teacher to **briefly restate the actual saved pending question once** (not the worked-example solution), while retaining exposure and learner-agency rules. The B2-F1 follow-up additionally makes the reconstruction question an **optional atomic companion** of `recordExposure(... requireReconstruction: true)` so the final exposure call persists both obligations before displaying the exact teaching Markdown. Older separate question calls remain accepted. No new learner state model, database schema, or scheduler was introduced.
- Narrow evaluation-fixture change: replace the ambiguous phrase “Later.” with the genuinely technically under-specified “It happens later.” and update its exact-response assertion. Do not interpret a learner's genuine request to postpone as a misconception.
- The other **twelve** tracked scenarios were not run by an independent model in this batch. Current software tests still cover their kernel invariants, not actual teacher responses.
- No human learning gains, cross-session retention, provider portability or owner approval is claimed. This is engineering and behavioral dogfood, not a longitudinal outcome pilot.

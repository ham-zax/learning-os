# B4 — Fresh-teacher multi-turn and crash-recovery pilot (2026-10-12)

**Scope:** A bounded, synthetic, conversational handoff evaluation on canonical WebHarness ARM, `/home/ubuntu/repo/learning-os`, using Claive workers with Codex `gpt-6-luna` and max reasoning effort. Each turn started a **different, fresh model session without the previous teacher's chat transcript**. The teachers operated through the real public Learning OS kernel on **three isolated synthetic SQLite databases**. These are scripted learner messages and model outputs, **not actual user sessions, validated learning outcomes, provider-wide portability or proof of long-term retention**.

## Three cross-session sequences

1. **Ambiguous retry → clarified full answer → assessment.** A fresh teacher saved the verbatim underspecified “It runs again.”, opened one neutral clarification and did not assess or reveal the answer (`c3bb57b04552`). Another fresh teacher (`a6774afb5fe3`) received a scripted complete prediction and explanation, consumed it against the existing pending question, verified and assessed it correctly, and closed the same attempt. The final database has exactly two answered subquestions, **one correct evidence event** with valid retrieval and **zero exposures**. It preserved both distinct learner responses exactly.
2. **Causal error → model timeout → repair recovery → learner reconstruction.** The first teacher (`7bad59404a41`) timed out **after** durably recording the learner's original wrong-model answer and one incorrect assessment, **before** showing any explanation. A different teacher (`f1adf783430b`) resumed the same assessed feedback state, persisted exactly one corrective exposure and one reconstruction question using the atomic kernel operation, then displayed the correction. A third fresh teacher (`13b036fda3f7`) received a scripted learner reconstruction, saved it against the pending question, resolved reconstruction and closed the session. Final state: one original incorrect assessment, one corrective exposure, one answered reconstruction question, and no invented mastery or extra assessment evidence.
3. **Interrupted scaffold → submitted assisted answer → model timeout → assessment recovery.** The first teacher (`d423f92a7b2b`) preserved the existing scaffold exposure and pending frozen question but **missed the conversation requirement**: it redisplayed the full pending question instead of explicitly acknowledging saved guidance and checking whether it arrived. A separate teacher (`a0b5e7fa853e`) then received a scripted correct response and saved it exactly, but timed out before deterministic verification. Another fresh teacher (`2a220b6f3b41`) resumed the pending verification/assessment and closed the same attempt. The original scaffold exposure remained exactly once; the final assessment is correct but `retrieval_valid = false` because guidance was recorded beforehand. No duplicate exposure or attempt was created.

The scaffold miss revealed a priority conflict: an early generic “redisplay pending question” rule overrode a later scaffold-specific interruption rule. B4 clarifies the **exception near the generic rule** in `skills/learning-os-teacher/SKILL.md` and `docs/teacher-agent-protocol.md`: on interruption, inspect `getSessionScaffoldPresentations` before redisplay, acknowledge recorded help and assistance status, briefly restate the saved pending question, ask once whether the guidance arrived, and replay teaching only if needed. A **newly seeded independent retest** (`e6f1e6b995a1`) explicitly followed this sequence, with 4/4 existing scaffold DB checks and no reply advisories. The original noncompliant reply remains preserved as diagnostic evidence, not relabeled as passing.

## Evidence and reproducibility

- Persistent scratch root: `/home/ubuntu/work/scratch/learning-os-b4-20261012/`. The read-only audit script `results/verify.py` validates final SQLite states, exact scripted learner inputs, permitted ARM tool routes, per-flow DB isolation, and no tool calls after the final `recordExposure` action. Its JSON evidence is `results/B4-manifest.json`. Raw model `result.txt` and event logs are under `/home/ubuntu/.local/state/claive/<worker-id>/` and remain **outside Git**. No private learner profile was opened or changed.
- **11/11 final scripted continuity invariants passed across all three sequences and the isolated scaffold interruption retest.** Two of the nine worker invocations **timed out** and are not represented as successful model replies; their partially persisted state is intentionally part of the recovery evidence. The other seven workers completed. The model's read-only audit recorded **zero non-ARM tool calls, foreign-database calls, disallowed evaluator/profile reads, or post-exposure tool calls** for these nine invocations.
- Learner responses and their sequencing are synthetic and fixed by the test operator. Verifying invariant outcomes does not establish that a learner understood the material. A correct assisted answer is *not* independent retrieval; an answered reconstruction question is *not* a new mastery event.
- The scaffold retest covers only the high-priority interruption rule. The model's completion in the two interrupted longer episodes does not prove low-latency tool use; model-timeout risk remains a separate operational consideration.

The earlier 16 individually tested synthetic teaching scenarios and this B4 pilot exercise different properties: B2/B3 check **single-turn kernel correctness**, whereas B4 tests **handoff over the same durable state** across independent model sessions. Neither replaces the still-outstanding owner-judged teaching assessment or a delayed, unassisted learning-outcome pilot.
